# Hardening before the first Community Applications release

Review of the office's own code (web side, mailbox, agent, desks, root jobs,
outgoing requests) on branch `task/hardening`. Each change is a commit
`Hardening: …`; tests are in `tests/run.php hardening`.

## Who gets in

The office's security is Unraid's login. The page and everything under
`/plugins/unraid-secretary-office/` are behind nginx `auth_request`, every POST
carries Unraid's `csrf_token`, and whoever is logged in to Unraid is root
(a single admin, the web terminal without a further password) — whoever
leaves Unraid logged in hands out root, with or without the office. So the
office has no lock of its own: it adds previews and confirmations against
mistakes (every changing action's dialog; the restore's and the Kopia setup's
«I have read what will happen»), not a second lock. Up to 1.27 a PIN could
guard changes; it only ever protected the old Compose stack's page (no Unraid
login in front) and went with it on 2026-10-06. An old `data/office/auth.json`
is no longer read (the agent says so once in its log).

## Checked and found fine

- **Web entry points:** everything under `/plugins/unraid-secretary-office/` is behind nginx `auth_request`; every POST needs Unraid's `csrf_token` (`local_prepend.php`); Unraid's session cookie is `SameSite=Strict`. The API changes nothing on GET (`state&fresh=1` only refreshes). POSTs also need `X-Office: 1` + JSON (CORS preflight) and a matching `Origin` — a second CSRF guard beside Unraid's token. Body ≤ 1 MiB, JSON depth 16. `agent/agent.php` runs nothing under a web SAPI (`PHP_SAPI === 'cli'` guard; desks only register functions).
- **Waking disks:** only on an explicit choice (`wake`, ticked in a dialog); whereabouts' `measure` of an array share runs `du` there and may spin its disks up — measuring, asked for by a click.
- **Commands:** all via `run()`/`runAll()`/`proc_open` array form; the only `sh -c` is the agent's own restart (`exec "$@"`, no values). `escapeshellarg` only for atd scripts. Ids are re-validated against a fresh scan (snapshots, plans, cleanup entries, setup decisions against the plan, logs by id never path, Docker names from `docker ps`).
- **Settings/cron/ini writers:** cron expressions (`cronValid`) admit only digits, `*`, `,`, `-`, `/`; consolidate.ini values single-quoted and checked against existing shares/pools; setup decisions: keys from the plan, values without control characters, setup.sh validates again; the menu label is limited to letters/digits/` .&+_-`; templates get `htmlspecialchars` (XML), override files single-quoted YAML with a refused-if-unusual parser.
- **Pages:** no `innerHTML`/`insertAdjacentHTML` with data anywhere (only `= ''` to clear); everything is built with `textContent` (`Office.el`), tooltips via `textContent`, dialogs take text or nodes. The config JSON in the page uses `JSON_HEX_TAG|JSON_HEX_AMP`; the Dashboard tile's HTML is `htmlspecialchars`-escaped server-side.
- **Secrets:** the Emby API key never reaches a state file or the page (`embySettingsPublic`), travels to curl in a 0600 header file in `/var/run/unraid-secretary-office` (0700) and to Emby as a header, never in a URL. State files hold only variable *names* of database passwords. `data/unraid-backup`, `data/embycache`, `data/gather`, `data/office` are 0700; the backup place is root-only 0700. `.env` files are never shown (only their path).
- **Root jobs:** `job.sh`, `agent.sh`, event scripts, the `.plg` install/remove: fixed paths, all variables quoted, notification arguments as an array, temp files only in root-only places (`/var/run/…` 0700, `/var/log`, the flash). atd scripts quote every argument.
- **Outgoing network:** release check https only; icon fetches `--proto =http,https --proto-redir =http,https --max-redirs 3 --max-filesize 1 MB`, timeouts, PNG magic checked; user-typed picture addresses http(s) only, `file://` only for candidates the office found itself (local PNG under `/boot`, `/mnt`, `/usr/local/emhttp`, no `/../`, awake disk). Emby: no redirects followed by curl.
- **Backup engine / gather** (spot checks only, shared files left alone): `docker exec … sh -c` only with variable names from fixed lists; logs carry variable names, not passwords; the gather quotes paths and uses `rsync -a` (links copied as links).

## Recommended, not changed

The engine's pruning already has its interface (`state/pruned.json`, engine 2.21).

- **Kopia's own config keeps the keys** (`<appdata>/kopia/repository.config` and `.kopia-password`): that is how Kopia works and how the nightly run connects — the same as when it is set up by hand, and that folder is in appdata (snapshotted, backed up). The Consultant says so before the keys are typed. For the few seconds Kopia runs, its environment holds them (readable by root only, `/proc/<pid>/environ`). Without HTTPS on Unraid's web UI they cross the LAN in clear, like the Unraid login itself.

- **State files owned by root instead of `nobody:users`.** `writeAtomic()` still defaults to `FILE_UID` 99. Anyone writing as `nobody` (guest on a public appdata share, PUID-99 containers that map appdata) can change `data/*.json`, which the page displays and a few agent paths read back (snapshot plans, notify state, release cache — now validated). Root-owned 0644 files would close this; left as is because "nobody:users like everything in appdata" is a deliberate convention. *(2026-10-06, still open: the change lies in `agent/lib/util.php` (`writeAtomic()`'s default owner), not in `plugin/scripts`.)*
- **`<appdata>/UnraidSecretaryOffice` owned by nobody** (`makeDataDir()`): whoever writes as `nobody` can rename `data` and put another folder there. The mailbox checks now stop requests from such a folder, but `data/office` (who is hired) would be the swapped one — that only changes the staff (Unraid's login stays). Suggest root ownership for that folder on fresh installs. *(2026-10-06, still open: the folder is made by `makeDataDir()` in `agent/agent.php`, not by `plugin/scripts` or the `.plg` — dropping its `lchown`/`lchgrp` there (root:root 0755 on fresh installs) is the change; existing installs keep theirs.)*
- ~~**`setup_plan` as an open action**, **`wake` on open actions**, **PIN lockout is global**~~ — done 2026-10-06, then obsolete the same day: the PIN and the open actions are gone (see «Who gets in»).
- **EmbyCache's urllib follows redirects** and forwards `X-Emby-Token` to the redirect target (also another host). Only a concern if the configured Emby URL redirects; a no-redirect opener would close it (EmbyCache code, left as is). *(2026-10-06, described only: `EmbyClient` in `embycache/embycache_lib.py` builds `urllib.request.Request(full, headers={"X-Emby-Token": …})`; urllib's `HTTPRedirectHandler.redirect_request()` copies such headers onto the follow-up request. The smallest fix: `req.add_unredirected_header("X-Emby-Token", self.api_key)` — urllib leaves unredirected headers off a redirect, so a redirecting URL then fails with 401 instead of handing the key on; or an opener whose redirect handler refuses (`redirect_request` returning `None` → `HTTPError`) with a clear message to enter the final address. Either goes into the list of our changes at the top of `embycache/README.md`; Jack Emby's own curl already follows no redirects.)*
- **VM names into `settings.ini`** (`[vm "<name>"]` in setup.sh): libvirt allows quotes; setup.sh's cross-check (`cfg_validate`) refuses a broken file, but an explicit name check in the engine would be cleaner (engine is shared, not touched here).

## Note for deploying

`dataDirTighten()` removes group/other write access from the data folder at
agent start. On a development server where `data/` is the clone's folder
(e.g. `drwxrwxrwx benj:users`) it becomes `drwxr-xr-x`: the owner keeps
access, other SMB users don't. Nothing of the office needs more (the web side,
Unraid's php-fpm as root, only writes into `mailbox/` and `office/`).
